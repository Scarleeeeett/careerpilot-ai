# CareerPilot AI 面试讲法

## 90 秒主线

我做的是 CareerPilot AI 求职诊断原型，解决海投过程中 JD 信息分散、准备动作难以复用，以及 AI 建议缺少证据的问题。

第一版我先选择固定 Workflow，而不是直接上多 Agent，因为 JD 解析、证据匹配、风险诊断和准备规划之间有稳定依赖关系。固定链路更容易控制输出结构、定位失败，也能在模型 API 不可用时切换到本地规则兜底。

之后我发现，仅展示最终结果不能证明系统可靠，所以把岗位理解、证据匹配、面试复盘、风险诊断、准备计划和投递文案全部补成带触发条件、输入字段、输出契约和失败边界的 6 个 Skill。`interview-retrospective` 会保留面试前准备快照，区分“系统是否准备到”“候选人是否答好”和“证据是否经得住追问”；`coverletter-tailor` 则校验 JD、真实经历、发送渠道和实习到岗条件。

评测上我保留了浏览器端 16 条工程回归和 15 条单标签路由 baseline，同时新增 12 条服务端自动化测试与 14 条完整执行计划评测。旧 baseline 仍暴露组合意图失败；新 Planner 能展开依赖，并避免把“评估准备覆盖”误路由成“生成准备计划”，当前样本为 14/14。

这个结果让我明确了架构边界：稳定任务继续使用固定 Workflow，开放组合任务由轻量 Agent Orchestrator 做任务拆解和多 Skill 串联。当前 Planner 仍是确定性规则，不是模型自主 Function Calling，所以 14/14 只能叫 Planner Exact Plan Accuracy，下一步才会评估模型工具选择和参数抽取。

## 高频追问

### 为什么不用多 Agent？

主任务依赖顺序稳定，固定 Workflow 的延迟、成本和失败归因都更可控。开放入口只增加一个轻量 Orchestrator，不把每个步骤包装成独立自治 Agent，避免不必要的延迟和失控空间。

### 你做的是真 Agent 吗？

当前是混合式求职诊断 Agent / Workflow 原型：真实模型负责结构化生成，确定性 Planner 负责多 Skill 计划，本地规则负责兜底；已经有统一入口、Zod 校验和节点 Trace，但还没有模型自主 Function Calling。

### 16 条工程回归和 11 条路由样本是不是太少？

是，所以它们只用于开发阶段的回归测试和 baseline 验证，不用于证明线上泛化能力。后续需要加入真实查询、边界样本，并对模型 Tool Calling、参数完整率、稳定性和成本进行人工校准。

### 匹配分怎么算？

它不是录用概率，而是规则证据维度覆盖分：候选人资料覆盖的 JD 能力维度数除以 JD 识别出的能力维度数。这个指标的作用是暴露简历缺证据的地方，不替用户判断能否拿到 offer。

### Coding Agent 帮你做了多少？

代码由 Coding Agent 辅助实现。我负责定义用户问题、Workflow 边界、模块输入输出、Schema、评测维度和 badcase 验收，并检查实现结果。不会把自己包装成独立完成全部工程代码的开发者。
